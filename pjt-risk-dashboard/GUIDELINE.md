## 1. 문서 정체성 및 작업 환경

### 1.1 이 문서의 역할
- Claude Code가 대시보드를 개발·갱신할 때 따르는 상세 설계서다.
- 필수 규칙 요약은 `CLAUDE.md`에 둔다.

### 1.2 작업 환경
| 항목 | 내용 |
|---|---|
| 개발 도구 | 보안 PC 내 VS Code + Claude Code (사내 사용 승인 완료) |
| 파일 이동 | 외부 → 내부 반입 가능 / 내부 → 외부 반출 불가 |
| 데이터 접근 | Claude Code는 실데이터를 읽고 처리할 수 있다 |
| 버전 관리 | 로컬 git (외부 원격 저장소 push 금지) |
| 금지 | 외부 원격 저장소 push, 외부 URL 호출, 외부 CDN 사용 |
| 열람 환경 | 사내 PC 웹브라우저 (Chrome/Edge) |

### 1.3 출력물 요구사항
- 형태: 단일 HTML 파일. 더블클릭으로 열리고 오프라인에서 동작한다.
- 기준일 선택: 누적된 스냅샷 중 보고 기준일을 선택해 조회한다.
- 출력: 브라우저 인쇄 → PDF. 별도 PPT 생성 기능은 만들지 않는다.
- **화면 = 인쇄물**: 화면에 보이는 그대로 A4 가로로 잘림 없이 인쇄되어야 한다.

## 2. 목표 및 성공 기준

### 2.1 목표
기존 PJT 손익 리스크 보고자료(PPT/엑셀)를 **대체**하는 마일스톤 기반 HTML 대시보드를 구축한다.
경영진이 **[ITC 기준 손익]**과 **[ITC 미반영 손익변동 영향요인]**을 구분해 파악하고,
마일스톤·트리거의 **지연 형태**를 한눈에 볼 수 있어야 한다.

ITC 개정은 연 1회이므로, 트리거 발생 후 ITC 편입 전까지(최대 약 12개월)의 손익 변동은
본 대시보드가 유일한 경영진 가시화 수단이다.

### 2.2 단계별 범위
| 단계 | 시점 | 범위 |
|---|---|---|
| MVP | 2026년 11월 보고 (10월 말 기준) | 단일 PJT, 기준일 선택, PDF 인쇄, 기존 보고서 필수 항목 100% 포함 |
| 2차 | MVP 운영 2~3개월 후 | 다수 PJT, 포트폴리오 합산 화면 |
| 3차 | 미정 | 추세 분석 등 |

데이터 구조는 MVP부터 `PJT코드`를 키로 두어 다수 PJT 확장에 대비한다. 화면은 단일 PJT만 구현한다.

### 2.3 MVP 완료 판정 기준 (전부 충족)
1. 기존 보고서의 필수 표·숫자(`docs/REPORT_SPEC.md` 기재 항목)가 대시보드에 빠짐없이 표시된다.
2. 대시보드 수치와 원천 엑셀이 원 단위까지 일치한다 (§7.3 검증 전부 통과).
3. 인쇄(PDF) 결과물을 별도 수정 없이 보고에 사용할 수 있다.
4. 다음 보고 시 엑셀 입력만으로 재생성된다 (코드 수정 불필요).

### 2.4 MVP 제외 사항 (요청이 와도 2차로 이관)
- 다수 PJT 화면, PPT 생성, 사용자 권한, 서버 배포, ERP 연동

## 3. 용어 및 손익 로직

### 3.1 용어
| 용어 | 정의 |
|---|---|
| ITC | 완성예측원가. 기투입 원가 + 향후 투입 추정원가 = 추정 최종원가. QG 승인으로 확정되며, 원가/ITC 진행률로 매출·매출이익을 산정한다 |
| QG (Quality Gate) | ITC 개정을 승인하는 내부 품의 절차 (전결규정에 따름). 통상 연 1회 |
| 경영계획 | ITC를 바탕으로 당해 연도 매출·손익을 월 단위로 배분한 계획. 연초 수립 |
| ITC 기준 준공손익 | 현재 승인된 ITC로 산정한 준공 시점 예측 손익 |
| 손익변동 영향요인 | 금액을 ITC에 포함할 수 없어 미반영 상태이나, 트리거 발생 시 손익에 추가 임팩트(+/−)를 주는 항목 |
| 트리거 | 영향요인을 현실화시키는 구체적 사건 (예: 협상 결렬, 발주처 공문 접수, 판정 선고) |
| Downside / Upside | 손익 감소 요인 / 손익 증가 요인. **별도 관리하며 상계하지 않는다** |
| 준공영향 | 준공 시점 총 손익에 미치는 영향액 (**주 지표**) |
| 당해영향 | 당해 회계연도 손익에 미치는 영향액 (보조 지표) |
| 스냅샷 | 특정 보고 기준일의 데이터 파일 1개 (`data/YYYY-MM-DD.xlsx`) |

### 3.2 금액 원칙
- 영향요인 금액은 **확률·범위 없이 단일 숫자**로 고정한다. 산정 가정은 `금액 산정 가정` 필드에 기록한다.
- 준공영향·당해영향 모두 **사람이 입력**한다. 대시보드는 회계 계산(진행률, 매출 산정, 당해영향 산정)을 하지 않는다.

### 3.3 요인 상태
| 상태 | 정의 | 합계 포함 |
|---|---|---|
| 트리거 대기 | 트리거 미발생 | 포함 (진행 중) |
| 트리거 발생 | 트리거 발생, ITC 미편입 (⚠ 중점 관리) | 포함 (진행 중) |
| ITC 편입 | 금액 확정 → ITC 개정·QG 승인 완료 → 종결. 편입 금액 기록 | 제외 |
| 소멸 | 트리거 미발생 확정 → 종결 | 제외 |

### 3.4 표시 공식
```
[준공 관점]
  ① ITC 기준 준공손익                                   (입력)
  ② Downside 반영 시 준공손익 = ① + Σ(진행 중 Downside 준공영향)
  ③ Upside 잠재액(준공)       = Σ(진행 중 Upside 준공영향)      ※ 별도 표시

[당해 관점]
  ④ 경영계획 연간손익                                    (입력)
  ⑤ 연간 전망손익 = 누적 실적 + 잔여월 계획              (입력)
  ⑥ Downside 반영 시 당해손익 = ⑤ + Σ(진행 중 Downside 당해영향)
  ⑦ Upside 잠재액(당해)       = Σ(진행 중 Upside 당해영향)      ※ 별도 표시
```
- ①(준공)과 ④(당해)는 서로 다른 관점이다. 하나의 브릿지로 연결하지 않는다.

### 3.5 절대 규칙
- 확률·가중치·기대값을 계산·표시하지 않는다.
- Downside와 Upside를 합산·상계한 수치를 어떤 화면·출력물에도 표시하지 않는다.
- 종결 요인(ITC 편입·소멸)은 합계에서 제외한다 (ITC와 중복 계상 금지).
- 금액 부호: Downside는 음수(−), Upside는 양수(+)로 저장한다.
- 저장 단위는 원, 화면 표시는 억원(소수 1자리)으로 한다.

### 4.2 스냅샷 파일 규칙
- 파일명: **보고 기준일** `YYYY-MM-DD.xlsx` (비정기 보고, 같은 달 복수 보고 대응).
- 한 파일 = 한 기준일의 전체 상태. 이전 파일은 수정하지 않는다.
- 작성자: 프로님이 현장 자료(양식 비통일)를 바탕으로 템플릿에 직접 작성한다.

### 4.5 백필 (과거 보고 3회분)
- Claude Code가 `00_원자료`의 과거 보고서를 읽어 해당 기준일 스냅샷을 작성한다.
- 원자료에 없는 필드는 **빈칸**으로 둔다. 추정해서 채우지 않는다.
- 백필 스냅샷은 PJT정보 시트 비고 또는 별도 표시로 `백필`임을 명시한다.
- 백필 결과는 프로님 검토·승인 후 확정한다.
- 백필 스냅샷은 필수 필드 검증(V1)에서 예외를 허용하되, 빈칸 항목은 화면에 "자료 없음"으로 표시한다.

## 5. 마일스톤 체계

### 5.1 원칙
- 대시보드 마일스톤은 5~6개로 제한한다 (핵심 공정 + 트리거 연결 이벤트).
- 마일스톤과 트리거의 **지연 형태**를 시각화하는 것이 핵심 목적이다.

### 5.2 지연 지표 (자동 계산)
| 지표 | 산식 |
|---|---|
| 누적 지연 | 예상일 − 기준일 (개월, 소수 1자리) |
| 직전 대비 지연 | 당회 예상일 − 직전 스냅샷 예상일 |
| 연속 지연 횟수 | 예상일이 연속으로 뒤로 밀린 스냅샷 수 |

트리거 예상시점에도 동일 지표를 적용한다
(기준값 = 해당 요인이 최초 등록된 스냅샷의 트리거 예상시점).

### 5.3 MTA(Milestone Trend Analysis) 차트 사양
- X축: 보고 기준일 (**실제 날짜 간격**, 비정기 보고 반영) / Y축: 예상일
- 마일스톤별 선 1개. 트리거 예상시점은 별도 차트 또는 구분된 선 스타일로 표시
- 대각선(기준일 = 예상일) 기준선 표시. 선이 대각선에 닿으면 완료
- 완료 마일스톤은 실적일에서 선을 종료한다
- 읽는 법: 수평 = 일정 유지 / 우상향 = 지연 누적 / 계단형 = 반복 연기

## 6. 화면 구성 및 인쇄 규격

### 6.1 화면 순서 (위→아래, 1단 세로 배치)
| 순서 | 영역 | 내용 |
|---|---|---|
| A | KPI 타일 | 1줄: 준공 관점 ①②③ / 2줄: 당해 관점 ④⑤⑥⑦ |
| C | MTA 차트 | 마일스톤 + 트리거 예상시점 지연 추이, 지연 지표 |
| B | 손익 브릿지 | ① → 요인별 Downside → ② (준공 관점, Upside는 별도 표기) |
| E | 변동 내역 | 직전 스냅샷 대비 신규·금액·상태·시점 변동, 종결 |
| D | 영향요인 표 | 전 항목. 상태 '트리거 발생' 강조 |

순서는 초안 검토 후 사용자 지시로 변경할 수 있다.

### 6.2 레이아웃 원칙
- 내부 스크롤 영역(가로·세로)은 원칙적으로 만들지 않는다. 불가피하면 사용자 승인을 받는다.
- 표는 줄바꿈으로 폭을 맞추고, 가로 스크롤을 만들지 않는다.
- 툴팁·펼치기 등 인터랙션에만 있는 정보가 없어도 인쇄물만으로 의미가 완결되어야 한다.

### 6.3 인쇄 규격
- 용지: A4 가로, 여백 10mm
- 각 영역(A~E)은 페이지 경계에서 잘리지 않는다 (`break-inside: avoid`)
- 모든 페이지 머리말: PJT명 · 보고 기준일
- 인쇄 시 기준일 선택 등 조작 UI는 숨긴다
- 색상만으로 의미를 구분하지 않는다 (흑백 인쇄 대비: 기호·선 스타일 병행)

## 7. 기술 구현 및 검증

### 7.1 기술 스택
| 구분 | 사용 | 금지 |
|---|---|---|
| 변환 | Python 3 + openpyxl | 그 외 패키지 (사용자 승인 없이 추가 금지) |
| 출력 | 단일 HTML (CSS·JS·데이터 인라인) | 외부 CDN, 외부 URL 호출, 외부 폰트 |
| 차트 | 인라인 SVG 직접 생성 | 차트 라이브러리 |

### 7.2 처리 흐름
```
data/*.xlsx  →  python scripts/build.py
                 ├─ ① 전 스냅샷 읽기
                 ├─ ② 검증 (§7.3) ── 실패 시 즉시 중단, 오류 목록 출력
                 ├─ ③ 대사표 생성 → output/reconciliation_<기준일>.md
                 └─ ④ HTML 생성  → output/dashboard_<기준일>.html
```
- HTML에는 전체 스냅샷이 포함되며, 화면에서 기준일을 선택한다.

### 7.3 검증 규칙 (하나라도 실패하면 HTML 생성 중단)
| # | 검증 항목 |
|---|---|
| V1 | 필수 필드 누락 없음 (백필 예외는 §4.5) |
| V2 | 요인ID·마일스톤ID 중복 없음, 과거 ID가 다른 항목에 재사용되지 않음 |
| V3 | 부호 일치: Down은 음수, Up은 양수 |
| V4 | 상태·유형·방향·구분 값이 허용 목록 안에 있음 |
| V5 | 마일스톤 기준일이 이전 스냅샷과 동일 |
| V6 | 종결 요인(ITC 편입·소멸)이 합계에 포함되지 않음 |
| V7 | 화면 KPI 값 = 엑셀 원천값으로 독립 재계산한 값 (원 단위 일치) |
| V8 | 변동 대사: 직전 합계 + 신규 ± 금액변동 − 종결 = 당회 합계 (Downside·Upside, 준공·당해 각각) |
| V9 | ITC 편입 상태 요인에 편입 금액 입력됨 |
| V10 | 파일명 기준일 = PJT정보 시트의 보고 기준일 |
| V11 | 마일스톤 예상일이 직전 대비 변경된 경우 지연 사유 입력됨 |

### 7.4 대사표 (`reconciliation_<기준일>.md`) 내용
- KPI ①~⑦: 엑셀 원천값 / 재계산값 / 화면 표시값 / 일치 여부
- V8 변동 대사 내역 (항목별 증감)
- 검증 V1~V11 결과 (통과/실패, 실패 시 행 위치)

### 7.5 AI 작업 규칙 (절대 규칙)
1. `00_원자료/`는 읽기 전용이다. 어떤 경우에도 수정·이동·삭제하지 않는다.
2. 원자료에 없는 숫자를 만들지 않는다. 불명확하면 빈칸으로 두고 사용자에게 질문한다.
3. 검증·대사가 실패하면 데이터나 계산식을 고쳐 통과시키지 않는다. 원인을 보고하고 사용자 판단을 받는다.
4. `data/*.xlsx`는 사용자 입력 파일이다. 백필 등 사용자가 지시한 경우에만 작성하며, 작성 후 사용자 검토를 받는다.
5. 한 번에 한 영역만 수정하고, 수정할 때마다 로컬 git에 커밋하며 `CHANGELOG.md`에 기록한다.
6. 본 지침과 충돌하거나 지침에 없는 결정이 필요하면 작업을 멈추고 질문한다.
